#### DECISION-050: `Stage.sprites` is drawn, and a sprite's natural size is the size it was drawn at
* **Date:** 2026-09-03
* **Status:** Accepted (closes half of DECISION-044's stated negative)
* **Owner:** Trevor (agent-assisted)
* **Context:** Playing the game, Butt-Butt-BONK and Goat Frontman had no art on them — the backdrop and the default bars, and nothing else. Neither is missing any: both ship a full slot set under `public/assets/scenarios/`, both build a complete `Stage` every frame, and their own suites assert on those sprites in detail. Nothing drew them. DECISION-044 wired `Stage.notes` and recorded `Stage.sprites` as still unread, which cost nothing while the only two playable families drew their actors through the transitional `prototypeLayer()` hook — CLIMB's climber and REPEAT's crusher. The two families added since own no prototype layer, so sprites are the whole of their visible output, and "unread" meant a scenario with a crowd of nine goats in its debug readout and an empty stage on screen.
* **Decision:** Draw them. `src/ui/timeline/stage-layer.ts` places and paints a minigame's sprites in the space `minigame/api.ts` already describes — `x` across the playfield, `y` down the lane band, both free to leave 0..1 — in two passes: `"under"` behind the note bars, `"over"` in front of them but still beneath the played-note row and the strike line, so the player's own note stays the top thing on screen. Within a layer, `z` then array order; a sprite with no layer is `"over"`, since an actor or an effect is the common case. Rotation turns about the anchor, so a `"bottom"`-anchored performer leans on its hooves. **A sprite's natural size is the size the art was drawn at:** one art pixel is `paneHeight / 216`, the height of the nominal 384x216 scene each art generator composes into, so `scale: 1` is the size the sprite would be in a scene that tall. Butt-Butt-BONK's ram and wolf, whose art came from a third-party pack drawn nearly three times larger than the generated art, take one family-level scale that brings them and their effects down together into the roughly two-lane range every other actor occupies, and the distance between them is spent to the **left**, over notes already played.
* **Alternatives Considered:** (a) Sizing from the row height, the way note art does, where `scale: 1` is one row tall. Rejected: it throws away the art's own proportions — Butt-Butt-BONK's 15x60 accent flash and its 37x37 impact burst would be drawn the same height — and it silently rescales every family's art the day the lane count changes. (b) Matching the backdrop's cover-fit scale exactly, so a sprite and the background share a pixel grid. Rejected: cover-fit is `max(width/W, height/H)`, so sprite size would follow the window's aspect ratio while the `y` placing it did not, and a family's careful "hooves at 1.27, horns reaching 0.994" would come apart at some viewports and not others. Height alone is aspect-independent. (c) Taking the unit from each scenario's own backdrop image, which is the same idea without the constant. Rejected on the evidence: Rocky's backdrops were redrawn at 768x288 for detail while its sprites stayed at their old scale, so a backdrop is not a statement about the art in front of it. The frame is a host convention, pinned in one place and documented as one. (d) Implementing the key-based cross-fade the contract's `Sprite.key` docstring promised. Rejected for now and the docstring corrected instead: these families swap poses on every note, and a cross-fade between two poses a sixth of a beat apart is a smear, not a transition. Keys stay required so the fade can be added without rewriting a shipped family. (e) Redrawing the Butt-Butt-BONK art smaller instead of scaling it. Rejected: `AGENTS.md` §11 — runtime transforms exist so that near-identical assets do not have to.
* **Consequences:** Positive — two of the four playable scenarios go from bare to fully dressed, and the contract's last unimplemented promise to a *new* family is kept, so a family with no prototype layer is now fully drawable: sprites are what TRAVERSE, BATTLE and every scenario after them will be built on. `tests/stage-layer.test.ts` pins the space, the size rule, the ordering, the missing-asset gap and that no shipped sprite would stand more than five lanes tall at `scale: 1`, which is the drift a fixed exchange rate invites. Negative — `Stage.background` is still unread, for DECISION-044's unchanged reason: the backdrop is its own canvas, fed by `backgroundId()`. The two prototype layers stay until the crusher's solved arm is baked. And the sizing rule is a **new host convention that both existing families were written before**: Goat Frontman's constants land almost exactly where their comments claim, Butt-Butt-BONK's needed the scale pass above, and a third art set at a third scale will need its own. The one thing now visible that was not before is that the frontman is the *least* visible thing on his own stage — a dark goat on a dark floor between white crowd goats — which is an art value problem, logged in `docs/IDEAS.md` rather than fixed here.

#### DECISION-049: A minigame is told the phrase length, and the shipped tests are re-pinned to the authored content
* **Date:** 2026-09-02
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted)
* **Context:** `npm run build` and `npm test` were both red on `main`. Three separate causes had piled up: `PERFORM_MINIGAME` never implemented the `backgroundId` member the module contract added, and three test files had drifted from the API (`AttemptRuntime` no longer emits an `energy` event, `parseLevel` is handed the whole level object); the Scale content redo (e1c9e35) moved Rocky Ascent's eighth-note material from L3/L4 up to L5/L6 and added L5-L7 across the ladder without re-pinning the tests that named those levels; and Goat Frontman's authored star ceilings were still the one-pass numbers from the branch where an attempt played its phrase once. Underneath the last of these, `flourishOpportunities` took its modulo from `plan.totalBeats` — the whole attempt — so a flourish authored at beat 3 was marked on the first pass and silently dropped on the second, which is the opposite of what its own doc comment promises.
* **Decision:** Add `phraseBeats` to the host-owned `AttemptContext.plan` — the length of the *authored phrase*, which an attempt plays `ATTEMPT_REPEATS` times — and take the flourish modulo from it. Regenerate `goat_frontman.scenario.json` with `scripts/author-goat-frontman.mjs`, which already reads `ATTEMPT_REPEATS` from `src/config/tuning.ts`. Update the drifted tests to assert the content that is actually authored, keeping each test's original intent (the eighth-note density cases move to L5/L6; the run-shell case now states that nothing in the shipped library is a content limit any more, since Rocky Ascent High authors L7).
* **Alternatives Considered:** (a) Deriving the phrase length inside `PerformMinigame` by importing `ATTEMPT_REPEATS` and dividing `totalBeats`. Rejected: how many times the host repeats a phrase is host business, and a family reaching into `src/config/tuning.ts` is exactly the ownership inversion AGENTS.md §"Scenarios Own" forbids. (b) Reverting the Scale content redo so the old tests passed again. Rejected: the redo is a deliberate design change with authored data behind it — the tests were the stale half.
* **Consequences:** Positive — `npm test` (583) and `npm run build` are green, so the Pages deploy can run; flourish notes now fire on both passes of an attempt, which is what the design and the docstring already said; Goat Frontman's ★★★ once again means every opportunity in the *attempt* taken at Perfect. Negative — `plan` grows a fourth field every future family has to understand, and no *normal* run can reach the "content-limit" ending any more, so the test that covers it now reaches an unauthored slot through the dev-only `difficultySequence` override rather than by playing the shipped ladder out. The rule stays covered; what is no longer covered is the shipped library happening to have a hole in it.

#### DECISION-048: ThreeStepMinigame ships, and Butt-Butt-BONK is the first scenario built from third-party art
* **Date:** 2026-09-02
* **Status:** Accepted (implements one of the five in DECISION-047, with the scenario changed)
* **Owner:** Trevor (agent-assisted)
* **Context:** Four of the six permanent families had no module and no scenario. DECISION-043 had already reduced adding one to an edit of `scenario/registry.ts`, so the blocker was art, and DECISION-047 established that `itch.io` and `opengameart.org` are reachable again. DECISION-047 proposed Hop-Hop-LEAP as the triplet scenario; the designer asked instead for triplets as a fight with wolves, by moonlight. That is not a `BattleMinigame` — the family-to-musical-family mapping is canonical (GDD §1.2), and `BattleMinigame` is Sixteenth Phrases — so it is a THREE-STEP scenario whose *target* is a wolf, which is exactly the catalogue's Butt-Butt-BONK: "two little preparatory horn taps followed by a major third impact; altered endings produce different victims or objects."
* **Decision:** Build `ThreeStepMinigame` (`src/scenario/minigames/three-step-minigame.ts`) and author Butt-Butt-BONK at L1–6. The family derives each note's A/B/C role from **its position within the beat**, never `index % 3`, rounding onto the loader's own twelve-tick grid. The ram acts on the **authored** target's lane, not the played pitch — terrain-bound like CLIMB, not a projectile like REPEAT. A group is credited only when both taps landed before the headbutt; the wolf drops to its bonked state on the headbutt and stands back up on the measure line, while the attempt-global group count survives it. Art comes from four external packs, vendored under `art-sources/` and cut to one static billboard per slot by `scripts/import-scenario-art.mjs`.
* **Alternatives Considered:** (a) Hop-Hop-LEAP, as proposed. Rejected in favour of the designer's ask; Butt-Butt-BONK is also the better scenario, because step C gets a target that visibly reacts instead of an inert rock pile, and it shares its whole art set with a future Wolf Pack. (b) Making it a `BattleMinigame` so the wolf could close in. Rejected: that family is Sixteenth Phrases, and re-pointing it at triplets would break the one mapping the six families exist to keep stable. (c) Fetching the art at build time rather than vendoring it. Rejected: a build that reaches the network breaks when a page moves, and a derivation nobody can re-run is one nobody can review. (d) Downscaling the external sheets to the placeholder art's 24x18 source resolution. Rejected: the existing art is small art the runtime scales *up* ~2.4x, so the external sheets already land near on-screen size, and non-integer downscaling destroys pixel art. (e) Binding one impact effect and scaling it for the big hit. Rejected as it would have been near-identical assets (AGENTS.md §11) — instead the two effects are an early and a late cell of one expanding ring, which are genuinely different pictures.
* **Consequences:** Positive — three of six families now ship, and the drum kit's **triplet** rhythm variant is selected by real content for the first time, closing half of a logged content gap; `tests/subdivisions.test.ts` now asserts the feel comes from exactly one scenario instead of asserting no scenario reaches it. Negative — this introduces the repository's **first CC-BY obligation**: Sevarihk's Mountain Goat Sprites is CC-BY 4.0, so `ASSET_SOURCES.md` is now a licence record rather than a courtesy one, and attribution has to survive any future art pass. Three existing tests encoded "five scenarios, none authoring triplets" and were updated deliberately; one of them named two families by hand where it meant "all of them", and now derives the set. The scenario stops at L6 per the catalogue, so the run's L7 content gap stays open. **Not verified by the repository's own toolchain:** `registry.npmjs.org` returns 403 in this container, so `vitest`, `tsc` and `vite build` could not run; the module, the loader path and every level were exercised instead under `node --experimental-strip-types` with a vitest shim, and a control run against `main` confirms this change introduces no new failures.

#### DECISION-046: A PERFORM scenario's flourishes are authored per note, and the crowd is spectacle that only grows
* **Date:** 2026-09-02
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted)
* **Context:** The Goat Frontman brief: on the notes marked `F` the goat hits a flourish pose; as it does, a crowd of other goats comes to watch; the higher the difficulty, the more goats. L1 repeats one of four variants; L2 picks two L1 variants and plays each twice, in any order; L3 is four harder variants; L4 picks two L3 variants and plays them twice. Two questions the brief leaves open: whether "pick" happens per attempt or once, and what a bad note does to a crowd that has already arrived.
* **Decision:** `PerformMinigame` (`src/scenario/minigames/perform-minigame.ts`) is a `MinigameModule` against DECISION-023's API and touches nothing else in the host: one `registerMinigame` line, one scenario entry. The flourish is authored **per note** in the prompt (`flourish: true`, a designer-readable mirror of the `F`) and per level in `visual.flourishBeats`, which is what the runtime reads; a test keeps them equal, and `create` throws if a flourish beat is not the start of a note. Flourish notes carry a star `overlay` on the timeline so the pose is visible before it arrives (GDD §1.4: difficulty from playing, not obscurity). The per-level ladder is one number, `goatsPerFlourish` (1 / 2 / 3 / 6, so the crowd a full phrase draws is 4 / 8 / 12 / 12 — L4 has half the flourishes of L3 and summons twice as many each rather than finishing with a thinner crowd). Perfect draws the full count, Good half. **"Pick" happens once, in `scripts/author-goat-frontman.mjs`** (L2 = variants 2,2,3,3; L4 = variants 2,3,2,3, alternating every bar because that is the one extra difficulty the pick order can carry); the unpicked variants stay in the file's `variantLibrary`. **Bad notes cost nothing that was earned:** the performer flinches, the crowd drops to its unimpressed state and slumps for a beat, and no goat ever leaves — the crowd is the attempt-global record, the same rule as the Rocky climb's "earned progress is never taken away". The crowd is impressed from ★★ and the payoff burst fires at ★★★.
* **Alternatives Considered:** (a) Rolling a variant per attempt so "in any order" is literal. Rejected: `AGENTS.md` §6/§18 — scenario exercises are hand-authored, and a per-attempt roll is procedural selection by another name; it is worth a class parameter later if the designer asks. (b) A goat walking off on a miss, as the mirror of one arriving on a flourish. Rejected: that charges twice for one mistake (the miss already cost the score and the flourish it was on) and puts the only interesting thing on screen behind the player's worst moments. (c) Deriving the flourish from the note (e.g. the last note of each measure). Rejected: L4's flourish is an off-beat eighth after a rest; the designer marks it, the data carries it. (d) Authoring L2–6 as the canonical catalogue lists Goat Frontman. Rejected in favour of the brief's L1–4 (`AGENTS.md` §20: the current explicit request wins); the deviation is recorded in the scenario file's `productionNotes`.
* **Consequences:** Positive — the class contains no scenario names, and the second PERFORM scenario is data and art; the scenario's own headless suite covers the brief's behaviour as `Stage` output, including that a Good flourish draws half a crowd, a missed one draws nobody and a wrong note takes nobody away. Negative — the crowd stands on the floor below the lane band and the performer straddles its bottom edge, which was placed from the normalised geometry and one browser look rather than tuned; and the Good-window floor from `main` (DECISION-038) is not on this branch, so an eighth-note flourish at 0.25 beats of lateness is a miss here and a Good there — the tests use 0.18 so they hold on both.

#### DECISION-045: Pentatonic material is authored as pentatonic, resolved by the run's mode, and written to fit the octave rather than folded into it
* **Date:** 2026-09-02
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted)
* **Note:** Numbered past `main`'s highest (DECISION-044 as of this merge) rather than against this branch's own log, which restarted at 023 and had independently reached 041/042 — both branches allocated numbers concurrently, colliding on 042 (this entry's neighbour) and nearly on 041 too, so both are renumbered here rather than duplicated, per the same reasoning DECISION-039 records.
* **Context:** The Goat Frontman brief (the first `PerformMinigame` scenario) was written by the designer in **pentatonic** degrees — `5Q 1Q 2Q 1QF` — with an explicit reason: the same Blues Lick is `6 1 2 1` in a major key and `b7 1 b3 1` in a minor one, so no roman numeral can be written down before the run's mode is rolled. The existing authored vocabulary (`1..7`, `b1`, DECISION-012) is diatonic and is parsed into a lane at load time, which is exactly the moment the mode is not known.
* **Decision:** A second authored vocabulary, `p1..p6`, parsed into a `PentatonicDegreeRef` (a step 1..5 and an octave band) and turned into a diatonic `ScaleDegreeRef` by one function, `resolveDegree(ref, mode)`, called from `game/targets.ts` — already the one place a degree becomes a pitch — using major `1 2 3 5 6` / minor `1 b3 4 5 b7`. Both are subsets of the run key's own scale, so every resolved target is diatonic and the lane labels the player reads stay right. The vocabulary spans **exactly the timeline's octave**, `p1` the root and `p6` the root above it, and `resolveDegree` moves nothing: a ref that could not be drawn throws.
* **The fold, proposed and dropped.** The brief's first draft counted eleven degrees around a *middle* root, five of them below it. The timeline is one octave with no lanes under the root, so that material was first shipped with the low octave folded up — right pitch class, wrong contour, behind a `PENTATONIC_LOW_OCTAVE_FOLDS_UP` flag and labelled provisional. Put to the designer as one of three options (widen the timeline, let a scenario declare its own lane window, or keep the fold), the answer was to keep the one-octave timeline and **rewrite the two licks that dipped below the root**. That is the better outcome and it deletes the flag: no note in the game is now drawn anywhere but where it was written. The middle-root material stays in this entry and in the scenario's `designerReview` as the thing worth restoring if the timeline ever spans two octaves.
* **Alternatives Considered:** (a) Transcribing the brief into diatonic tokens by hand, twice, one file per mode. Rejected: the run picks the mode, a scenario is one file, and the transcription would be a lie in one of the two. (b) Widening the timeline to two octaves. Reverses DECISION-012, touches the lane model, the fingering picker, the played-note row and every renderer, and lands in the middle of the minigame-API refactor; the designer chose to keep one octave. (c) A per-scenario lane window — a scenario declaring "root in the middle, a fifth either side". The most interesting of the three and the one to reach for if a second Blues Lick scenario wants a middle root; it is a host change and wanted coordinating with the refactor rather than slipping underneath it. (d) Keeping the fold. Rejected once the material was rewritten: a display rule that moves a note is worth having only while some scenario needs it, and none now does.
* **Consequences:** Positive — the notation the designer writes in is the notation the file is in; nothing is folded, clamped or moved, so the timeline silhouette is the phrase's true shape (GDD §13.1); `p7`..`p11` are now parse errors, so a scenario still written in the old two-octave vocabulary fails loudly instead of resolving to some other note; and both `scenario-registry.test.ts` and this scenario's own suite check every authored target is a real lane in *both* modes. Negative — the licks now resolve *to* the root rather than turning around it, which is a slightly less bluesy shape than the brief's first draft, and that is a real cost of the one-octave timeline rather than of this decision.

#### DECISION-044: The host owns every note rect; a minigame answers with three slots around it
* **Date:** 2026-09-02
* **Status:** Accepted (implements `GOATerizer_Minigame_Authoring.md` §4)
* **Owner:** Trevor (agent-assisted)
* **Context:** `Minigame.render(view) → Stage` had been in the contract since DECISION-043's predecessor and both families implemented it, but **nothing called it** — the seam sat in the tree for fifteen commits with every browser check green over a completely dead surface, because the host inks that canvas whether or not a minigame draws a pixel. Meanwhile a target was a rounded rect in a judgment colour, so Rocky's timeline had no terrain on it at all. The question the design has to answer is not "can a scenario supply art" but "what can a scenario supply art *for*, without being able to make the challenge harder".
* **Decision:** The host computes every target's rect once, in `TimelineView.#targetRect`, and uses it twice — to draw the bar, and as the read-only `PlacedNote.rect` handed to the minigame. A minigame answers with up to three slots per note: `body` is stretched to the rect exactly, so duration stays honest; `underlay` and `overlay` draw at natural size **centred** on it and bleed freely outside — the rect is an anchor, not a clip. The playfield is the one clip a skin cannot escape. The host washes every skinned note with its outcome colour — judged or not — and draws the played-note row and strike line above everything. Stages resolve per attempt key, because two attempts share the timeline across a transition and each is skinned by the minigame that owns it.
* **Alternatives Considered:** (a) One `assetId` per note. Rejected: it forces terrain, glow and ornament through one image whose aspect ratio has to match a rect that changes width with duration. (b) Letting the minigame supply the rect. Rejected outright — `AGENTS.md` §12: a skin that could move, resize or hide a note could make a challenge harder or easier through visual ambiguity, and the signature is where that is prevented, not a convention. (c) Clipping ornament to the rect. Rejected: it is exactly the overdraw the three slots exist for — neighbouring crags overlap into one ridge line only because they bleed. (d) Washing only *judged* notes with their colour, which the first draft did. Rejected after looking at it: it turned every upcoming target to grey stone, making the thing you are about to play the least visible object on the timeline. (e) Computing the rect separately for drawing and for the contract. Rejected: two computations can drift, and a skin anchored to a rect the host does not draw on is the ambiguity this whole decision exists to prevent.
* **Consequences:** Positive — Rocky's bars are stone ledges on a crag again, and the crag at 1.55 rows wide fills in solid behind the climber as the phrase is played. Three browser checks bind it, and they are deliberately **not** `canvasHasInk`: the control is Can Crushing, which returns no note art at all and must count zero, so the differential is a real product difference between two families rather than a debug toggle. Injecting a `render()` that returns null drops Rocky's count from ~640 px to 0 and fails, which is the proof. Negative — `Stage.background` and `Stage.sprites` are still unread. The backdrop is its own canvas behind the timeline, so a background clipped to `span` would be a second, disagreeing answer to where the art goes; that closes when the backdrop folds onto this canvas. And the crusher control has to be read under the flawless tier: the Good-note colour is too bright for the green probe at full strength but lands squarely inside it under the judgment wash, which counted five Good notes as scenario art until the check moved.

#### DECISION-043: Both minigames become registered modules, and the host stops knowing which family is playing
* **Date:** 2026-09-02
* **Status:** Accepted (supersedes the `minigameClass` discriminant in `PROPOSED_Timeline_Actors.md` §7)
* **Owner:** Trevor (agent-assisted)
* **Context:** `src/minigame/api.ts` had been restored to the tree but **nothing implemented it**: the only files importing it did so for a type. Family dispatch was still in the host at four sites — `AttemptRuntime.#driveActor`/`#driveRepeat`, two `kind` branches in `game-app.ts`, and `loadScenario`'s `KNOWN_CLASSES`. Every one of them meant that adding a third family was an edit to the loader, the runtime and the renderer, which is the difference between "the game supports six minigames" and "the game can be given a minigame".
* **Decision:** `CLIMB_MINIGAME` and `REPEAT_MINIGAME` are `MinigameModule`s registered at the composition root (`scenario/registry.ts`), wrapping main's `TimelineActor` and `RepeatMinigame` state classes unchanged. `#driveActor`/`#driveRepeat` become each module's `onJudged`; `AttemptRuntime` keeps one `#toJudged` speaking only the contract's vocabulary. The binding and parameter parsers move out of `load.ts` into `parseConfig`/`parseLevel`; `MinigameClassId`, `ScenarioAssetBindings`, `ScenarioClassParameters`, `RouteData` and the per-family binding types leave `types.ts`, and `config`/`data` become opaque `unknown`. `assetIds(config)` replaces `climbAssetIds`/`CAN_CRUSHING_ASSET_IDS`; `backgroundId(config)` replaces the backdrop reading a binding by name; the dev panel's per-family rows become each module's `debug()`.
* **Alternatives Considered:** (a) Keeping a `kind` discriminant and a union of binding types. Rejected: it is the compile-time union the open `MinigameId` exists to remove, and every family added widens types the host has no reason to know. (b) Handing the module the `RunKey` so it could call `laneOfMidi` itself. Rejected: a family that can read the key can start grading pitch, and grading is the host's — the module derives the same answer from `Judged.lane` instead. (c) Baking the crusher's IK arm to a pose ladder as part of this, so the actors could move into `Stage.sprites` too. Rejected as scope: 866 lines of canvas primitives with a solved elbow is its own piece of work and is not what makes a family pluggable. `prototypeLayer()` stays, marked TRANSITIONAL, as the last place a family is named in the host.
* **Consequences:** Positive — adding a third family needs no edit to `types.ts`, `load.ts`, `attempt.ts` or `game-app.ts`. The registry refuses a module built against a different `apiVersion` and refuses a duplicate id, so a content error fails loudly rather than playing as whatever happens to be first. Negative, and it caught a real regression on the way: `#driveRepeat` placed a can with `laneOfMidi`, which is null off the scale, and a null lane is what makes a can wobble; `Judged.lane` is the *continuous* coordinate, so a major third in a minor key lands at 3.5 and rounding it invented a lane the player never played. `placeableLane` takes integer coordinates only. Also `prototypeLayer` and the two `set*` layer paths in `timeline-view.ts` remain, so the host still has one branch on what kind of character a scenario draws — narrower than four sites, but not zero.

#### DECISION-042: A triplet is a duration name, positions are derived on a tick grid, and the Good-window floor is capped at the neighbour
* **Date:** 2026-09-02
* **Status:** Accepted (amends DECISION-039's flat `GOOD_WINDOW_FLOOR_BEATS`)
* **Owner:** Trevor (agent-assisted)
* **Context:** GOATerizer could hear a triplet but not author one. `subdivisionsOf` already detects a triplet grid from note positions so the drums can mark it, and Triplets is one of the six permanent families — but `NoteDuration` had no member for a third of a beat, `TIMING_WINDOWS_BEATS` had no row to judge one against, and `load.ts` required `durationBeats` to equal the table value exactly. The obstacle is arithmetic: 1/3 is not a binary fraction, so no decimal an author can type is exactly a third and no float sum of three of them is exactly a beat.
* **Decision:** Add `eighthTriplet` (1/3 beat) to `NoteDuration`, `DURATION_BEATS` and `TIMING_WINDOWS_BEATS` (`perfect: 0.08`, `good: 1/6`). In the loader the duration names become the authority: length comes from the table, position from a running sum on a 12-tick-per-beat integer grid — twelve because it divides both the binary subdivisions and the triplet one — and the `durationBeats`/`startBeat` a file states are verified within `AUTHORING_TOLERANCE_BEATS` (0.01) and discarded. `subdivisionsOf` also consults the new name, for a triplet whose other two thirds are rests. **And the Good-window floor is capped at the nearest neighbour's distance:** `good = max(good, min(GOOD_WINDOW_FLOOR_BEATS, nearestGap))` — a Good window may reach as far as the next target's own attack, but never past it.
* **Alternatives Considered:** (a) Keeping authored `startBeat` as the runtime value with a loosened tolerance. Rejected: a written `0.333` is 0.00033 off, past `subdivisionsOf`'s 1e-6 epsilon, so the drums would stop marking the very grid the notes are on — and twelve of them miss the phrase end by 0.004 beats. (b) Accumulating derived positions as floats. Rejected for the same reason at smaller scale: three thirds sum to 0.9999999999999999. (c) Leaving the flat 0.5 floor. Rejected: it is three times a triplet's neighbour gap, and on the one-pitch material a THREE-STEP scenario is made of, pitch filtering cannot disambiguate what that lets through. (d) Exempting `eighthTriplet` from the floor by name. Rejected as a special case the next dense subdivision would have to remember to opt into; the cap is one rule that covers all of them. (e) A `tuplet: {inSpaceOf}` modifier per note, as notation software does. Rejected as more expressive than the roster needs, and it would put a second length field in front of every minigame reading `Opportunity.duration`.
* **Consequences:** Positive — the family is unblocked, and the cap is provably invisible to everything that ships: all five scenario files use only `half`, `quarter` and `eighth`, whose nearest neighbour is never closer than half a beat, so `min(0.5, gap)` is 0.5 for every one of them. `tests/timing-forgiveness.test.ts` and `judgment.test.ts` pass untouched, which is the proof. The tick grid also makes existing content exact by construction rather than by luck. Negative — the triplet timing row is a guess, flagged as such, and it is the subdivision Tuninator is least accurate on. A duration not on twelfths needs `TICKS_PER_BEAT` revisited: a sixteenth triplet (2 ticks) fits, a quintuplet does not. And a triplet's windows now overlap its neighbours' by construction, so "one played note resolves one target" is a structural guarantee from `#findMatch` rather than a geometric one — pinned by its own test.

#### DECISION-040: One pick is one played note, however many `Note`s the recognizer splits it into
* **Date:** 2026-09-01
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** Recovered from `claude/tuninator-experimental-recognition-lcrsuv` while clearing branches, rather than written fresh — the analysis was done in August and never landed. Tuninator segments one played event into more than one `Note` a measurable fraction of the time: **97 of 459 events** in its own corpus. Downstream a fragment is indistinguishable from a second pick, so the first `Note` resolves the target and the second lands as a **wrong note** — one cleanly played note scores as a hit *and* a mistake, and draws two bars on the timeline. That is the same symptom DECISION-038 chased from the other end ("the goat appears briefly then disappears"): the actor falls on a wrong note exactly as it falls on a miss, so a phantom second note kills a goat that had just been spawned by the real one. Two independent mechanisms, one appearance.
* **Decision:** A `Note` that starts within `FRAGMENT_COALESCE_MS` of an already-announced attack is folded into it rather than announced: silently when it agrees about the pitch, as a `retune` when it does not, since that is the same information a `pitchCorrection` carries. Every later event about that `Note` — including its release — travels under the original attack's id, and the release fires only when the *last* `Note` carrying that attack stops sounding, so a bar does not end while the string is still ringing under a fragment. The window is bracketed rather than chosen: the floor is 80ms, Tuninator's own `transient.articulationMs`, below which it has already absorbed the stub itself, so a shorter window would miss exactly the splits that escape; the ceiling is 107ms, a sixteenth at the fastest tempo the game offers, above which a genuine fast re-pick would be swallowed. 90 is the only round number comfortably inside.
* **Alternatives Considered:** (a) Leaving it to Tuninator. Rejected: the library reports what it hears, and what counts as one *played note* is a question about this game's rules, not about detection — `AGENTS.md` §4's boundary stays intact because no pitch detection happens here. (b) Measuring the window from the previous fragment's *end* rather than from the attack. Rejected: `releaseGraceMs` means a legato eighth ends only as the next one begins, so a contiguity rule would swallow real playing. (c) Porting the branch whole. Rejected — most of it had already landed independently: its `src/persistence/calibration.ts` and its "apply suggested trim" button are the same idea as `src/persistence/latency.ts` (identical storage key) and the timing-check screen, which is a fuller version.
* **Consequences:** Positive — the branch's nine-test adapter suite ports unchanged and passes against a provider that has been rewritten since, which is decent evidence the rules were the right shape. Four deliberate breaks fail it. Negative, and it is a lesson rather than a defect: the branch's own "a genuine re-pick is still announced" test derives its gap from `FRAGMENT_COALESCE_MS`, so widening the constant widens the test with it and the assertion moves out of the way — a mutation to 400ms passed. The ceiling is now asserted against the tempo and subdivision tables instead, which the adapter cannot move. **Not ported:** the same branch's `nearestPitchDelta`, which measures how far a played note fell from the nearest target of its pitch *ignoring every window*, so latency calibration can bootstrap on a rig sitting outside the Good window entirely. That is a real answer to a gap recorded in `docs/IDEAS.md` and is left there rather than smuggled in under a branch cleanup.

#### DECISION-039: `?key=` and `?tempo=` are setup links, not developer flags
* **Date:** 2026-08-28
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Note:** Recorded as DECISION-020 on `claude/url-variables-key-tempo-m67zbn` and renumbered to 039 when that branch met `claude/timeline-actors-draft` on main — both branches had allocated 020 concurrently. The number is this file's index, so a duplicate is worse than a gap.
* **Context:** The run key is rolled from a weighted table (`config/key-weighting.ts`) and the tempo starts on Billy Goat, so practising one particular key — Eb major, weight 3 out of ~132 — means rerolling until it comes up. Every existing URL parameter in the game is gated behind `?dev=1`, which raised whether pre-setting the key and tempo belongs behind that gate too.
* **Decision:** `?key=` and `?tempo=` are ungated. Both name a choice the pregame already offers by hand (Reroll, the tempo chips), so a pre-set link is a shortcut into normal play rather than a way around it. They set the *starting point* only: Reroll still rolls a fresh weighted-random key, the chips still switch tempo, and nothing pins the setup for the rest of the run. * **Alternatives Considered:** (a) Gating both behind `?dev=1`. Rejected: dev flags exist for things unreachable from normal play (injected input, forced difficulty, autoplay); a key and a tempo the player can already pick are not that. (b) Honouring an arbitrary `?tempo=100` literally. Rejected: the five tempos are design (GDD §3.4) and high scores are tracked per tempo, so a sixth bpm would invent a tempo the scoreboard has no column for — snapping keeps the request meaningful without doing that. (c) Treating the params as a pin that Reroll respects. Rejected: Reroll is an explicit player action with one meaning, and a Reroll button that re-rolls the same key would be broken; the link is the starting point, the pregame is still in charge. (d) Rejecting a spelling like `D#` in a flat key. Rejected: the pitch class is unambiguous, and refusing to start over a spelling preference would be hostile to a hand-written link.
* **Consequences:** Positive — "the Eb one again" is a shareable link, the awkward keys become practisable without grinding the reroll button, and the two parsers are unit-tested (round-tripping every key in the weight table through `keyShortName`/`keyDisplayName`) rather than living as inline string handling in the app shell. Negative — a key reached by link bypasses the weighting the distribution was tuned around, so a player who links their way to one key sees none of the variety the table exists to produce; and the enharmonic acceptance means the URL and the on-screen readout can legitimately disagree (`?key=D#` → `Eb`), which is correct notation but reads as the game ignoring the link.

#### DECISION-038: Judgment gets a floor under it, because a shifted performance is not a bad one
* **Date:** 2026-09-01
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** First real-guitar report of the run: "I only see the goat appear briefly then disappear. It's saying my timing is bad... but it isn't. It needs to be more forgiving of the timing. Maybe even within an eighth note it can register as correct." Two symptoms, one cause, and it was measurable the moment it was looked for. `computeWindows` clamped every Good window to half the distance to the nearest neighbouring target, so eighth-note material was judged at ±0.25 beats — 167ms at 90bpm, which is *inside* the uncompensated latency of an ordinary interface. Past that point a note arrives after its own target has expired and `#findMatch` offers it to the nearest one still open, which is the next target and a different pitch: the player is charged twice for one late note, a **miss and a wrong note at once**. Simulated against the real judge on authored material: sixty targets, a hundred and twelve failures, and it arrives as a **cliff** rather than a slope — at 0.20 beats nothing fails, at 0.25 half of it does, at 0.30 all of it. The actor falls on either a miss or a wrong note, so the goat never survived two notes. Separately, the timing check told the same player their notes were "too loose for the middle of them to mean anything" at a median deviation over 45ms, which is a session player's consistency, and refused them a latency trim — the one thing that would have fixed the underlying problem.
* **Decision:** `GOOD_WINDOW_FLOOR_BEATS = 0.5` — half a beat, an eighth note either side, at any tempo, whatever the subdivision and whatever the clamp says. The player's own framing, and it doubles the tolerable offset from ±0.20 to ±0.40 beats (±267ms at 90bpm) on eighth material, one-pitch material and scale material alike, in both directions. Perfect is deliberately **not** floored: widening what counts as a hit is forgiveness, widening what counts as flawless would make three stars mean less. `MAX_USABLE_SPREAD_MS` goes 45 → 70 and the copy stops implying the player is at fault. And `?dev=1&playOffsetMs=N` now exists, because nothing in this repository could produce the input that breaks it.
* **Alternatives Considered:** (a) Leaving the clamp and treating this as a latency problem to be fixed with the timing check. Rejected as the whole answer — the offset is real and worth fixing, but a game that becomes unplayable at 167ms of latency is too brittle regardless, and the check itself was refusing to help. (b) Proportional windows (nine tenths of the gap rather than half). Measured as slightly better on quarters and *worse* on one-pitch material at large offsets, and it does not say anything a player could hold in their head. "Within an eighth note" does. (c) Keeping the non-overlap invariant. Examined and found to be protecting something the resolver already guarantees structurally: `#findMatch` filters candidates by pitch, takes the nearest survivor, and never offers a resolved target again, so one played note cannot resolve two whatever the windows are.
* **Consequences:** Positive — the reported symptom is now a browser check that reproduces it end to end (`playOffsetMs=200`): with the floor, `perfect/good/miss 0/6/0` and a live goat on a six-note streak; with the floor removed, `0/3/42` and the actor dead. Five unit tests pin the tolerance as *behaviour over offset* rather than as the arithmetic that sizes windows, which is the form the old tests should have taken — every one of them played on time, which is exactly why a total collapse under a constant offset shipped with a green suite. Negative, and stated rather than smoothed over: on **one-pitch material** the fix is not complete. Can Crushing is a single pitch for a whole attempt, so pitch cannot disambiguate anything and a shifted performance really does slide its attribution by one note; the slide is invisible mid-run and shows at the two seams where the rhythm changes, costing one miss and one wrong note at each — four events in forty-eight, against forty-eight before. The test bounds it at ten percent rather than claiming zero. Also negative: the autoplay planner jittered hits by a fraction of the Good window, which is now wider than the gap between notes, so it had to be re-bounded by the gap — a synthetic guitarist jittered by half a beat schedules its next pluck before the current one ends.

#### DECISION-037: A landing is the same landing at a different weight
* **Date:** 2026-08-31
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** "Make a big one land heavier." The actor's `size` (0..1, from the streak) fed exactly one thing — its overall scale. A twelve-note streak was therefore a *bigger* goat playing a *smaller* goat's landing, and mass that does not change how a body moves reads as a zoom rather than as weight.
* **Decision:** One pure function, `landingWeightFor(size)`, holds everything a landing does differently when the actor is heavy, so "heavier" is stated once rather than sprinkled through the drawing code: it deforms further (0.16→0.34) and settles slower (decay 0.14→0.28, wobble 26→16); it **holds at the bottom** for 0→0.05 beats before the spring starts, which is hitstop and is the strongest cue of the four — the pause *is* the mass; it throws 5→14 motes, further, for longer; and it presses into a darker shadow that spreads harder. Two options from the proposal were deliberately not taken: an asymmetric hop arc (changes flight, not landing) and a lane shockwave. Screen shake and a landing thud were argued against rather than deferred — shake would move the note bars the player is reading ahead on, and an extra transient on every note muddies the beat in a game whose whole input is rhythmic.
* **Alternatives Considered:** (a) Scaling only the squash. Rejected: one channel means the whole read depends on catching a frame or two, which is exactly why the previous version's landing was easy to miss. (b) Strict volume preservation for the squash, which is what was already there. Rejected once it was *seen* at the new depth: taking all the widening in one axis flattened a heavy goat to twice its own length and it read as a different animal lying down. The width now grows as the square root of what the height lost, which is also the more honest model — a solid flattening spreads into two horizontal directions and the view shows one.
* **Consequences:** Positive — verified as a light/heavy pair of strips from one run (size 0.58 against 1.00), and nine tests that assert *behaviour over time* rather than restating the table: does it compress further, is it still moving when the light one has stopped, is it held at full compression two frames in. All five deliberate breaks fail them, including removing the hitstop and flattening the weight table. Also fixed in passing: the streak sparks were inside the squash transform and stretched with the body, which reads as a rendering fault rather than as a body under load. Negative — the dust clamp exists because measuring found the puff already crossing the strike line at full streak, throwing debris over the read-ahead zone; that is fixed and tested, but the same measurement showed the **goat's own body** overhanging the line by about 21px at rest and 34px at the bottom of a heavy landing, roughly a fifth of a beat. That is not fixed. It predates this pass (it arrived with DECISION-036's size increase), the fix is a composition change the player has twice approved the current framing of, and it is parked as a question in `docs/IDEAS.md` rather than taken quietly. `actor-layer.ts` rule 1, which claimed the actor is never right of the line, now says what is actually true.

#### DECISION-035: The gate sets itself while the player warms up — and it now actually reaches the recognizer
* **Date:** 2026-08-31
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** "It does it during gameplay and not once it starts receiving a signal? I play a lot during the pregame screen. It should start as early as possible." Driving it in a browser to check rather than reading the code produced two findings, one reassuring and one not. The measurement *was* already running from the first frame after the mic opened — measured at 242ms after the click, on pregame, with a full recommendation 1.5s later — so the premise that it waited for gameplay was not true of the measurement. Measured directly: across an apply, the recognizer's state never left `listening`. The gate was stored, displayed, and never handed to Tuninator until the next page load. So the feature genuinely did not work *while you were playing*, which is exactly the shape of the complaint, arrived at from the outside.
* **Decision:** Four changes. **(1)** `#switchProvider` gains a `force` flag and `#applyInputGate` uses it — the gate is a construction-time option, so taking effect means standing a new recognizer up. The playing subset is now a suffix of one sorted array found by bisection, and the derived state is memoised, because three readers want it per rendered frame.

Rejected once the apply bug was measured: the user's report was correct about the feature even though the stated mechanism was not. (b) Leaving it a button. Rejected — the original request was "can it auto calibrate", so a control the player has to find is the fallback, not the mechanism. (c) Auto-applying anywhere, including mid-run. Rejected: rebuilding the recognizer during an attempt would drop the player's input mid-phrase, and pregame is the one screen where it costs nothing. (d) Sizing the window from Tuninator's hop size, which I inferred as ~86 frames/s. Measured instead and got 20.5, four times lower — at the inferred rate the window would have been a minute and a half of audio rather than twenty-five seconds.
* **Consequences:** Positive — measured end to end on the live recognizer: the gate now sets itself 4.7s after the mic opens with no interaction, the recognizer is genuinely rebuilt (`recognizers built: 1 → 2`), the value is stored, the button correctly stops offering a gate it already set, and Reset survives. Negative — automatic calibration changes the detector's behaviour without being asked, which is a real thing to do silently; the mitigations are that it only ever moves the gate *down*, demands more evidence than a human would, says what it did in the readout, and is one click to undo. And the thresholds behind that decision are still reasoned rather than validated against a real guitar — same standing caveat as DECISION-034, now with more riding on it. Also found while measuring: the suite's note claiming Chromium's fake capture device is silence was wrong — it is a pulsing tone, strong enough to measure a level from, which is why these checks can exist at all.

#### DECISION-034: Calibrate the detector's gate to the player's rig, not the player's rig to the detector
* **Date:** 2026-08-29
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** "I have to turn up the gain on my audio interface for it to recognize notes... I can't turn it up because then it blows out my amp sim. My amp sim uses the unamplified signal just fine, so tuninator should be able to, too." That last sentence is the whole diagnosis: an amp sim only amplifies and has no gate to fail, so a signal it reads perfectly can still be entirely below a detector's amplitude gate. Tuninator gates before it looks for a pitch, at `min(rmsGate, noiseFloor * 200)` — a **cap, not a floor**, so the adaptive term only ever lowers it, and on any rig whose noise floor is above about 4e-5 the flat 0.008 default binds regardless of how clean the signal is. GOATerizer passed no `engine` block at all, so that default was in force for everyone with no way to change it.
* **Decision:** Measure the rig and pass `engine.rmsGate`. A pure module (`game/input-gate.ts`) watches Tuninator's `pitchFrame` diagnostics — which carry `rms` on *every* frame including gated ones, which is what makes measuring a rejected signal possible at all — and takes the noise floor as a low quantile and the playing level as the median of frames above it. The recommended gate is the tightest of: Tuninator's own default (never make a loud rig deafer), half the player's notes (a gate above the notes rejects the notes), and the largest of eight times the noise floor, a hundredth of the playing level, and an absolute minimum. It is offered in pregame, stored per rig like the latency trim, and applied by rebuilding the recognizer through the existing provider-switch path.
* **Alternatives Considered:** (a) A software gain stage — the obvious reading of "auto calibrate its sound level", and wrong: gain after the converter raises signal and noise together, so it moves nothing measured as a ratio. Gain before the converter is the only gain that buys signal-to-noise and that knob is on the player's desk. **This was my first answer and it was half wrong**: the gain half is true, but the conclusion that nothing could be auto-calibrated was not — the gate was always the right axis. (b) The 2-in interface hypothesis, that a guitar on input 2 was being halved by a downmix. Investigated and refuted from Tuninator's source: it **sums rather than averages**, explicitly to avoid that 6 dB loss. Per-channel RMS and the selected channel are surfaced in pregame anyway, because that failure otherwise looks exactly like a dead detector. (c) Clamping a pathological measurement onto the nearest legal gate. Rejected: where "under the notes" and "above the minimum" contradict there is no right answer, so it recommends nothing and says the signal is too quiet to work with.
* **Consequences:** Positive — a player running a conservative interface into an amp sim can be heard without driving their interface into the sim, which was previously the only fix available to them. The measurement is pure and unit-tested against synthetic rigs, so "a quiet rig ends up with a gate under its own noise floor" is a test rather than something you need an interface to discover. Negative, and it is the important one: **the numbers are reasoned, not validated against a real guitar.** The eight-times-the-floor margin, the hundredth-of-signal term and the minimum gate are all arguments, and the rig that motivated this has never been measured. Two real bugs came out of driving it end to end rather than trusting the unit tests — a synthetic source has a mathematically zero noise floor, which put `Infinityx` in front of the player and collapsed the gate to its absolute minimum instead of scaling it to the signal.

#### DECISION-033: The backing is mixed for the speaker it is played on, and the kit marks the subdivision the exercise actually contains
* **Date:** 2026-08-29
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** First real playtest of the backing: "If there are drums at all they're not obvious. There definitely isn't anything coming in on the and between beats. It's a faint bass line." Measurement showed the eighth hits *were* being scheduled and sounded — in-game onsets were 330ms apart, which is an eighth at 90bpm — so this was never a scheduling bug. It was three separate things, none of which any test could see. The hat was a 45ms burst high-passed at **7kHz** and the sixteenth tick a 22ms burst high-passed at **11kHz**: small speakers roll off at the *top* as well as the bottom, so both measured as strong energy above 800Hz and were heard as a faint shimmer or as nothing. The bass was a sawtooth at 40–75Hz behind a 1.2kHz low-pass at 0.34 — the missing-fundamental reasoning was right, but a saw's harmonics fall away as 1/n and the octave arrives at half amplitude, which is not enough to reconstruct anything on a laptop. And the suite's one audio check measured **pregame**, which always plays the bare quarter-note pulse, so the entire in-game subdivision layer was untested.
* **Decision:** Three fixes and one new guard. **(1)** Voice the kit for the band a small speaker is honest in: the hat gains a 3.2kHz body under its bright burst, and the sixteenth tick moves from an 11kHz high-pass to a 6kHz band-pass at nearly three times the level. **(2)** Give the bass an explicit octave doubling at 0.42 under the fundamental, putting real energy at 80–150Hz, and raise its bus from 0.34 to 0.46. **(3)** Put a soft clipper on the master so this can be done without clipping — linear below 0.7 and bending smoothly above, so it is inert during ordinary playing and rounds peaks instead of squaring them. Separately, **the rhythm variant now follows the material**: `RhythmVariant` gains a fourth value, `quarters`, and eighth-note material selects `eighth`. Quarter-note material gets nothing between the beats, because a subdivision the exercise does not contain is the drummer counting something the player is not playing.
* **Alternatives Considered:** (a) A `DynamicsCompressorNode` as the limiter — tried first and measured worse than nothing: it is a level detector with an attack, so the transients that actually clip here are through it before it responds. (b) A normalised `tanh` waveshaper, mapping full scale to full scale — a trap, and it was caught by measurement rather than by reading: it gives everything *below* full scale a gain of up to 1.4, so every measured band got louder. That is a distortion pedal, not a limiter. (c) Simply raising the drum bus and the bass gain. Rejected: the problem was spectral, not level — energy above 7kHz does not become audible on a laptop by being louder, it just eats headroom.
* **Consequences:** Positive — at an unchanged full-band peak the audible band rose sharply (>800Hz peak 0.444 → 0.663 in pregame, at 0.668 → 0.701 full-band), and the kit now says what the exercise is: measured in-game, L1 produces 1.50 onsets/s at 90bpm (quarters) and L4 produces 3.00 (eighths). A new browser check, Part 1d, measures that *in a minigame* and would have caught the untested-subdivision hole. Negative, and worth stating plainly: **that check guards timing, not audibility.** Mutation-testing it — removing the hat's new 3.2kHz body — left it passing, because the kick and snare share the band and a 7kHz-only hat still leaks enough skirt into it. Whether a hit is *loud enough for a human on a laptop* is not something this rig can assert; the before/after numbers are evidence the mix changed, not a regression guard that it stays changed. Also fixed in passing: cancelling a scheduled bass note stopped only its fundamental and would have left the new octave sounding through a reroll or tempo change; and the Can Crushing slot check read the dev panel in the same turn as the click, a race that only surfaced once the suite grew slow enough to lose it.

#### DECISION-032: More ways to deal the octave, so the picker offers every hand position the neck can hold — and G is a register ceiling
* **Date:** 2026-08-29
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** "When picking which octave and hand position in the pregame screen, try to add options with roots on the D and G strings." `ROOT_STRINGS` already permitted E/A/D/G, so nothing was forbidding the higher roots. A survey across all 24 keys found the picker offering E=33, A=45, D=20, G=5. The cause was the shape table: only two note-per-string distributions existed, both spanning three adjacent strings, and rooted on D or G those groups cross the **B string**, whose major-third tuning pushes the upper notes a fret higher and out of the load-bearing five-fret window, where the span filter silently dropped them.
* **Decision:** Ship five more distributions — `3-2-3`, and the four-string `2-3-2-1`, `1-3-3-1`, `1-2-3-2` and `1-3-2-2` — which absorb that offset by redealing notes or by spending an extra *string* rather than extra frets (four strings buy 15 semitones against the octave's 12, so the hand never reaches). Then thin the result to **places to put the hand** rather than fingerings: one offer per `(rootString, lowestFret)`, tightest span winning, then at most two per root string keeping the lowest and highest. Both rules are blind to which string they thin — there is no quota propping up D or G. An exhaustive search over every deal of eight notes across two to six adjacent strings, all 24 keys, established that only **eight** distributions can ever fit five frets; seven ship, and the one left out (`2-2-3-1`) is excluded on measurement rather than taste — it lands on the same fret as `2-3-2-1` in every key it fits, so it moves no count and no position.
* **Alternatives Considered:** Widening `DIAGRAM_FRETS` or relaxing the span filter to force high-rooted shapes into existence — rejected, and this was the load-bearing rejection: the hand staying in one position is the entire point of the one-octave rework, and manufacturing options the neck cannot hold would quietly undo it. Also rejected: a per-string quota favouring D and G (props options up rather than finding them); raising `MAX_FRET`, which was probed and is not the binding constraint anywhere (at 15, 22 or 100 the G string yields the same 8 candidates at the same two frets); and `2-2-2-2`, which never fits, because two diatonic notes cover one or two frets while a string change buys five semitones, so the shape walks backwards down the neck faster than the scale climbs it.
* **Consequences:** Positive — the picker now offers **every hand position the neck can hold**, which is a stronger claim than "more options" and is what the completeness test asserts. An independent enumeration against all eight ever-fitting distributions initially found **20 reachable-but-unoffered positions across 16 keys**, including F major's D string, which was showing fret 1 when fret 0 was reachable; shipping `1-3-2-2` closes all 20, for two extra chips in total. Final counts across 24 keys: E 33→41, A 45→45, D 20→26, G 5→5 (total 103→117, avg 4.29→4.88 chips per key, **worst-case row unchanged at 6**). The number of keys offering two distinct D-string hand positions doubled, 6→12, and the mean separation between a key's two D-string offers went 2.17→3.00 frets — the D count is capped by the two-per-string rule, so the gain shows up as the pair being genuinely far apart rather than as more chips. Tablature View needed no changes: four-string shapes never put more than three notes on a string, so the gutter's fixed width still holds. Negative, and the honest part: **G did not move, and cannot.** The low root must be *on* the root string and the lane pitches are fixed, so the root has exactly one possible fret per string — `tonicMidi - openString`. With `LOWEST_TONIC_MIDI = 45` pinning tonics to A2..G#3, that fret is negative on the G string in 20 of the 24 keys. Eight G-rooted candidates fit in total, occupying five distinct positions, and the picker offers all five. Raising it would mean moving the register the whole game is written in, which is not a decision a fingering picker should be allowed to force.
* **Note on the record:** the commit that introduced this (`2c5f6ca`) describes six shipped distributions and E 33→39. Seven shipped and E reached 41: `1-3-2-2` and the completeness fix landed in the working tree between the verification run and the `git add`, and went in unremarked. The code in that commit is correct and is what the numbers above describe; only its message understates it.

The kit previously played one groove for the whole run, varying only by which subdivision it was marking.

Rejected: inaudible as *difficulty*, and it would have meant fading out the pulse the player depends on — hence `PULSE_FLOOR`, below which the kick, snare and on-beat hat never scale, since DECISION-016 measured that losing the on-beat hat drops the peak above 800Hz from 0.49 to 0.14 and that is as true at difficulty 1 as anywhere. "Minimal" means sparse, never inaudible. (b) Carrying a `SubdivisionSet` through so two grids could sound at once. Rejected: the design rule is one feel per minigame, and committing to one keeps the timbre that names a grid unambiguous. (c) Per-level authored drum data in the scenario files. Rejected: the beat is a property of the difficulty scale, not of scenario content, and 21 hand-authored bars per scenario is the authoring burden `AGENTS.md` §3 exists to prevent. (d) A two-measure loop with a bar-line crash. Rejected: attempts start 33 beats apart, so an 8-beat loop would land its "big" measure somewhere different relative to the phrase every time.
* **Consequences:** Positive — the kit now states what kind of exercise is starting before the first note. This **supersedes DECISION-016's look-ahead**, where the kit marked the union of the current *and next* attempt's grids to warn of a sixteenth run one minigame early; the beat now describes the exercise in hand rather than trailing the next one, and `unionSubdivisions`/`subdivisionKey`/`NO_SUBDIVISIONS` were deleted with it. Negative, and worth knowing before tuning any of it: **no authored level currently selects a variant.** All 20 levels across all five scenarios resolve to `straight`, because the material tops out at eighths — so the sixteenth and triplet patterns are implemented and unit-tested but never sound in play today, exactly like difficulty 7's rung, which also has no content behind it. Also unmeasured: the drum bus has no limiter, and rungs 6–7 (crash plus ride plus kick on every beat) could not be measured in the browser because nothing authors those difficulties; the cymbal peaks are deliberately low and earn their size from length, and `browser-validate.mjs` measures 0.75 full-band today against a naive 1.35, but this wants re-measuring against pinned L6/L7 content once it exists.

#### DECISION-030: The backing bass ducks when the player is missing, on a ladder even in decibels
* **Date:** 2026-08-29
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** "When a player is supposed to start a note, if the correct pitch note isn't started within a correctness register window, make the bass line progressively quieter. After four missed notes the bass should be almost silent, so the drums are prominent. When the player starts a note at the correct time or ends a note at the correct time the volume can restore. It takes 4 correct events for the volume to restore to normal." An accompanist who keeps playing at full volume while the soloist falls apart is being oblivious rather than supportive.
* **Decision:** A pure state machine (`src/game/backing-duck.ts`) turns judgment events into a 0..1 multiplier, applied by `BassPlayer.setDuck` as a 40ms ramp on top of the bass's existing 0.34 base level, so "the bass is subordinate by design" still lives in one place. Five rungs, spaced evenly in **decibels** rather than linear gain — −5dB per missed note, bottoming at −20dB (0.1) rather than silence. Symmetric: one rung down per `MissedNote`, one up per correct start or correct release, so four correct events restore full volume. Reset per attempt. To make "ended a note at the correct time" observable at all, `TargetJudge` gained a `release()` path emitting a new `NoteReleasedOnTime` event, scoped to the target's existing neighbour-clamped Good window around the note's *end* — no second timing table — and excluded explicitly, with a comment at each site, from the score, the star meter, the timeline actor and the can crusher.
* **Alternatives Considered:** (a) A linear ladder (1.0/0.75/0.5/0.25/0). Rejected: the ear hears ratios, so a linear ramp sounds like nothing happened for two rungs and then falls off a cliff. (b) Silencing the bass entirely at the bottom. Rejected: the bass is the player's only harmonic reference — it is where the key is — so muting it takes *information* away from precisely the player who most needs it. Barely there is a comment on the performance; absent is a punishment. (c) Ducking on `WrongNote` as well. Rejected: a wrong note does not consume its target, which expires as a `MissedNote` on its own if nothing correct arrives, so counting both charges one fumble twice — and it would penalise the player groping for the right fret more than the one who does not try, and would duck the band for noodling between targets. (d) A separate authored release-window constant. Rejected as a second timing table to keep in step with `TIMING_WINDOWS_BEATS`; reusing the target's own Good window means "released on time" works out to *held at least half the written note, let go before half again as long*, at any tempo. (e) Instant recovery on the first good note, which turns the whole effect into a flicker.
* **Consequences:** Positive — the backing now reacts to the performance, and the drums (which never duck) carry the floor when the player is lost, which is when an unambiguous pulse matters most. A clean note is worth two correct events, its attack and its release, so a player recovering on sustained material climbs back in about two notes while one on staccato material climbs at one rung per note; that asymmetry is intentional and tested both ways. Negative — releases now reach judgment for the first time, which is a genuinely new channel into a core system: the guard is `tests/attempt-and-run.test.ts`, where a flawless run *with* every note released on time must score identically to one without, because authored ★★★ thresholds are denominated at exactly `noteOpportunityCount * JUDGMENT_POINTS.perfect` and a single point for a release would make three stars reachable on a non-flawless run, by a different amount per scenario. That guard was mutation-tested. One documented hole: a note released before a late `retune` promotes it from wrong to hit never reports a release, costing one rung; the alternative is a replay mechanism inside the judge. If Tuninator turns out not to deliver reliable releases on the live path, nothing breaks — the duck simply recovers on attacks alone.

#### DECISION-028: The can crusher's read is his loop, not his crush
* **Date:** 2026-08-28
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** "The mechanic does not read." The first `RepeatMinigame` build was verified, screenshotted and shipped, and then failed the only test that matters: shown the result, the reader could not tell it was a can being crushed. Three things were wrong and none of them was the art. (1) The performer *only moved when the player succeeded* — arms up idling, dropping for a third of a beat when a can happened to land — so the animation that explains the game only ever played after the player had already done the thing it was meant to teach. (2) Cans rode at bar level, so a crush was a can at his feet turning squat; there was no place on screen that meant "put a can here". (3) A crushed can blinked out of existence and the pile silently incremented, so nothing connected the crush to the score. A missed note, meanwhile, produced no can at all: the one riding in simply vanished at the strike line, giving the worst outcome the least feedback.
* **Decision:** Make the performer's hand loop to his forehead and back *continuously*, hit or miss, note or no note, and phase-lock that loop to the authored note grid (`strikePeriodBeats`, the tightest gap in the material, snapped to a period that divides a beat) so the palm is down on every grid position a can can arrive at. Move him to a whole beat back from the strike line rather than 1.2, so a can born on the grid arrives on the grid — which is to say precisely when his palm is down. Give every note a can for its whole life, and let the outcome decide only *where the can gets to*: a placed can rises out of its bar into the gap under his palm over its beat of flight, a wrongly-placed one rises just as eagerly to the lane the player actually played, and a missed one is never lifted at all — it tips over and rolls past his boots. Make the lift a constant offset above the can's own lane, not a per-lane lookup, so the daylight between a wrong can and his hands is exactly the interval the player missed by. Make the crushed can fall from his brow onto the heap rather than teleporting into it — forward as it falls, so it drops clear of him instead of sliding down through his own face. And build the performer as a *figure*: joints at human fractions of his height, bones of fixed length, and the elbow solved for by the standard two-bone construction, mirrored for the arm that braces — with the side of that solve chosen by a fixed pole vector in body space (outward, and a little down) rather than by rotating the shoulder-to-hand line.
* **Alternatives Considered:** (a) A free-running idle loop at a fixed rate, with the crush retiming the hand when a can arrives. Rejected: the loop is the *promise* — retiming it makes the promise conditional on succeeding, which is the original bug in a new place. (b) Keeping the crush an absolute duration in beats. Rejected after measurement: at sixteenths the palm recovers in 0.07 beats while a 0.22-beat crush was still showing, so the flat can hung at his brow with nothing on it; both the crush and the fall are now capped as fractions of a swing. (c) Choosing the elbow's side by rotating the shoulder-to-hand line, which is the obvious way to do it and is wrong. That rotation follows the hand: with the hand raised it points outward, but with the hand *low* it points inward, and the bracing arm — the one on screen every single frame — folded its elbow through his own ribs. A pole vector in body space cannot do that, because it does not depend on where the hand is. A test now walks the swing and asserts every elbow stays on its own side of him and no closer to the midline than its shoulder; it fails against the old solve. (d) Leaving the arm as it was — a shoulder, a hand, and an "elbow" at the midpoint between them. That is what made it read as a tentacle: with no fixed bone lengths, lifting the hand simply lengthened both segments, and at the top of the swing the arm was nearly as long as the man. It was also load-bearing for the swing's shape, because the real constraint is that his reach is barely longer than the distance from his shoulder to his own forehead — which is why the hand now travels on an arc out to the side rather than straight up, where there would be almost no visible travel at all. (e) Verifying the rewrite from screenshots, as the first build was. Rejected, and this is the load-bearing one: a phase-locked loop *aliases* against a fixed-interval screenshot burst, so every frame comes back with the arm in the same place. A whole pass was spent debugging a loop that was working correctly. The geometry now has its own test (`tests/repeat-layer.test.ts`) that drives the layer against a context recording where it drew, and asserts the four spatial claims the read rests on.
* **Consequences:** Positive — he reads as a person rather than as a stick figure with one enormous limb, and the arm cannot stretch again by construction: a test drives the layer through a swing and asserts both bone lengths and the shoulder are unchanged frame to frame. The mechanic states itself before the player has got a single note right, the wrong-note feedback is diagnostic without any code knowing what an interval is, and every point scored is visibly delivered into the pile that becomes the trophy. A missed note now has feedback at all. Negative — the swing rate is a property of the whole scenario rather than of the passage being played, so material that mixes quarters and sixteenths gets a man working in sixteenths throughout; and at that rate several crushed cans are falling at his feet at once, which reads as a stream rather than as individual cans. Both are arguments for the between-measures walk the design already anticipates. The screenshot script now samples at varying intervals, which is a workaround for aliasing rather than a cure — the tests are the real guard.

#### DECISION-026: A timing check with its own screen, at 90bpm, on quarter notes
* **Date:** 2026-08-23
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** DECISION-024 put the calibration in pregame, and pregame is the wrong room for it. The bass loop is playing and the instruction is "noodle", so a note played there is as likely to be aimed at the music as at the beat — and at 120bpm+ a player cannot tell whether being off the timeline is the rig or their own hands, which is the exact confusion the measurement exists to resolve.
* **Decision:** Its own screen, off the start screen, with four choices that each rule out a way of measuring the wrong thing. **Quarter notes, not eighths** — a sample is matched to the nearest beat, so an offset past half a beat folds onto the wrong one; quarters at 90bpm give ±333ms of headroom before that, eighths would give ±167ms, which is inside the range of a bad Bluetooth rig, and eighths add the player's own subdivision error to a measurement that is not about subdivision. **90bpm, pinned** — a fixed reference is comparable between sessions, it is the game's own default, and hand synchronisation gets measurably worse below about 75bpm where the gaps are long enough that a player estimates rather than entrains. **The game's own quarter pulse, not a special click** — a sound's perceived onset depends on its attack, so calibrating against a sharper click than the one played over would bake in the difference. **Nothing on screen moves on the beat** — a visual pulse is a second cue, and a player given two cues splits the difference, which would make this a measurement of that blend rather than of the audio offset the judge compensates. Two bars count in, one bar is played and thrown away (the first notes of any tapping task are finding the tempo, not playing at it), four bars are measured. `CalibrationSession` unwraps against its own running median, which roughly doubles what can be resolved past the fold-over.
* **Alternatives Considered:** (a) Pairing the k-th played note with the k-th expected beat instead of rounding, which removes the fold-over entirely. Rejected: guitar onset detection drops notes — a re-struck open string may not register a second attack at all — and one dropped note shifts every pairing after it. Nearest-beat is free of that, and unwrapping recovers most of the range. (b) A mic loopback, still the honest way to isolate rig latency from the player. Not this: browsers apply echo cancellation to `getUserMedia` by default and it exists specifically to remove speaker sound from the mic. It remains the next step, with `echoCancellation: false`.
* **Consequences:** Positive — the offset and the spread are reported as two separate numbers in the player's own words ("your offset", "your consistency"), which answers "is that me or the game?" directly rather than making them infer it. The spread also gates the offset: too loose and the screen says play more evenly instead of handing over a number. Negative — what is measured is *not* pure rig latency. It includes the player's own anticipation, which is typically 20-50ms early for a musician. That is deliberate for a game, where the goal is that "on the beat" means what the player feels it means, but it does mean the stored trim mixes two things and is not portable to a different pair of hands. The screen is named and worded for that; the code says so where the number is defined.

#### DECISION-025: One clock, and it is the one the player hears
* **Date:** 2026-08-23
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** "Seems like a lot of latency with the beat." It was not a feeling. `Transport.beat` is the beat being *scheduled*, and audio written at context time `t` reaches the ears at `t + outputLatency + baseLatency`, so the raw transport clock runs that far ahead of the room. The timeline was drawn on it, so the note bar crossed the strike line before the drum hit arrived — imperceptible on a wired output, a third of a beat at 90bpm on Bluetooth. Worse, played notes were already timestamped in *compensated* time (`#toBeat` subtracts the same latency) while the judge was **ticked** in raw time, so its windows closed a full latency early and a note played dead on the beat could be marked missed before its own attack was delivered. The visual cue and the audible cue also disagreed, so a player following the screen was judged early and a player following the beat was judged late.
* **Decision:** Split the two clocks explicitly and name them. Scheduling audio stays in raw transport time — that is what `contextTimeAt` is for, and the bass and drums are unchanged. Everything downstream of the speakers — the timeline, the actors, the judge's tick, attempt completion, the transition slide, the attempt's own start beat — runs on `#heardBeat`, which is `beatAt(now − outputLatency − baseLatency − trim)`. Both cues then say the same thing and the existing input compensation is finally correct.
* **Alternatives Considered:** (a) Compensating the visuals only, leaving the judge on the raw clock. Rejected: that fixes the feel and leaves the early-expiry bug, which is the half that costs the player notes. (b) Shifting the audio later instead, scheduling everything a latency into the future so it lands with the visuals. Rejected: it makes every tempo change and every attempt boundary depend on a number the browser can revise mid-session, and it adds real delay to a game whose whole loop is "play a note, see it judged".
* **Consequences:** Positive — one clock for everything the player experiences, and a class of timing bug that could only show up on rigs nobody develops on is gone. The lead-in before the first note is now measured in heard time too, so it is the length the constant claims on every rig. Negative — `#heardBeat` reads `AudioContext.currentTime` once per access rather than caching per frame; it is a property read and the frame loop takes it once, but it is a footgun for future call sites. Anything scheduling audio must keep using the transport directly, and only the comment on `#heardBeat` enforces that.

#### DECISION-024: The player measures their own rig, and the game remembers
* **Date:** 2026-08-23
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** DECISION-025 fixes the part of the latency the browser knows about. The rest — a USB interface's own buffering, an amp in the chain, Bluetooth headphones the browser under-reports — is invisible to `AudioContext` and was a dev-only number in a hidden panel that reset on every reload. There was no way for a player to find out how late they were, and no way for the game to keep the answer.
* **Decision:** Calibrate in pregame, against the beat grid. Pregame already runs the transport, the drums and the microphone, so every note the player plays there is measured against the nearest beat (`offBeatMs`) and fed to the existing `TimingDeltaLog`. A Timing block shows both halves of the compensation — what the browser reported and what the player added — and, once there are at least eight notes clustered tightly enough that the median describes a rig rather than a warm-up, offers to apply the measured bias. The result is remembered in `localStorage`, clamped to ±500ms.
* **Alternatives Considered:** (a) A mic loopback: play a click, detect it in the input, subtract. It is the gold standard and it measures the true round trip with no reliance on browser reporting — but browsers apply echo cancellation to `getUserMedia` by default and it exists specifically to remove speaker sound from the mic, so the measurement is fighting the platform. Worth revisiting with `echoCancellation: false`, and noted as the next step if playing along proves too coarse. (b) Auto-applying the bias without asking. Rejected: it would change judgment mid-run, silently, on the strength of a player who might just be rushing.
* **Consequences:** Positive — the question "how much latency do I have?" is answerable by anyone, in the room, with their own guitar, and the answer survives a reload. The dev panel's trim now goes through the same setter, so the two controls cannot disagree. Negative — the measurement is only valid up to half a beat (±333ms at 90bpm), because past that `Math.round` picks the next beat and the error folds over; a worse rig has to calibrate at a slower tempo, and nothing but the readout tells the player so. It also assumes the player is aiming at beats, which in pregame — where the instruction is "noodle" — they may not be.

#### DECISION-021: Authored pitch places terrain; played pitch places projectiles
* **Date:** 2026-08-22
* **Status:** Proposed (drafted on `claude/timeline-actors-draft`)
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** Once the note bar is a container an actor stands on, the question is what a *wrong* note puts in it. Letting the played pitch place everything is the more responsive answer, and for a climber it is fatal: a flub could put the goat on a ledge the next authored note is unreachable from, so one mistake ends a run.
* **Decision:** Split by what the object is. **Terrain** — anything the actor stands on or has to reach — comes from the authored pitch and is therefore deterministic and readable seconds ahead. **Projectiles** — anything that resolves at the strike line and leaves no state — come from the played pitch. `ClimbMinigame`'s goat lands on `judgment.target.lane`, never on what was played. `RepeatMinigame`'s can appears at `laneOfMidi(judgment.playedMidi)`, and is crushed only if that is the performer's own lane. Off-scale or unpitched input spawns a can wobbling rather than snapping it to a lane it does not belong on.
* **Alternatives Considered:** (a) Played pitch everywhere. Rejected above. (b) Authored pitch everywhere. Rejected: wrong-note feedback then says only "wrong", where a can arriving two lanes high says "you overshot by a third" before the player can think about it — the projectile channel is the only place in the game that reports *how* you were wrong, in the moment.
* **Consequences:** Positive — one sentence decides where every future class's objects come from, and no class needs a special case. Negative — it constrains authoring for stationary performers: while the crusher does not move, every note in his material must be on his lane, or correct play triggers the failure animation. Can Crushing L1–4 are authored entirely on the root because of it, and a test enforces it.

#### DECISION-019: One seeded performance planner, two sinks; a tier picks its own input source
* **Date:** 2026-08-28
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** Autoplay was a loop inside `game-app.ts` with two hardcoded timing offsets and a "drop every fifth note" rule. It could not express "half correct", never played a wrong note, did nothing at all when a live microphone was the source, scheduled only one beat ahead, and — on the injected path — emitted no `release`, so every played bar grew from its attack to the playhead until it pruned. A demo mode needs a repeatable *imperfect* performance, and "imperfect" means fumbles that are provably fumbles under a judge that matches whole pitch classes across every open target.
* **Decision:** A pure `src/dev/auto-performance.ts` turns `(targets, mode, seed, attemptIndex)` into attempt-relative gestures and never reads a clock; `game-app.ts` keeps only the two sinks and the schedule lifecycle. Tiers are `perfect` / `50` / `25` / `off` — later joined by `75`; the set is data in `AUTOPLAY_HIT_RATE` and adding one is a line there, which is the point. Wrong pitches are chosen against the union of every target's *clamped* Good window, by pitch class, so octave equivalence cannot turn a fumble into a hit, and never repeat inside the wrong-note debounce, which would otherwise swallow the event and draw the bar as an ordinary played note. Picking a tier switches the source to `synth` **only when the current source cannot be a sink** — a live microphone cannot, the deterministic test provider can. Both sinks emit a real note-off.
* **Alternatives Considered:** (a) Auto-switching away from `input=test` as well. Rejected: `scripts/browser-validate.mjs` drives its whole first run on the test provider and asserts exact outcomes ("three stars for a flawless attempt"); moving it onto real detection would trade a deterministic suite for a flaky one, and the test provider is a perfectly good sink. (b) Capping an unreleased played note's drawn length in `TimelineModel`. Rejected: a genuinely sustained note *should* grow, and a cap would hide the producer bug rather than fix it — so the producers were fixed and an `unreleased played` counter was added to the dev panel instead, which also surfaces real Tuninator dropping a `noteEnded`. (c) Seeding from `Date.now()`. Rejected: the point is a link that replays.
* **Consequences:** Positive — the fake guitarist is unit-testable against the real `TargetJudge` with no microphone, intent and outcome agree exactly on the deterministic sink (asserted), `?dev=1&autoplay=50&seed=7` is a shareable demo, and every attempt is now scheduled a whole attempt ahead instead of one beat. Negative — up to ~64 oscillators can be scheduled at once on the synthetic path, so cancellation is mandatory rather than optional (`SyntheticGuitarSource.cancelFrom`); the synthetic path's *achieved* rate runs under the intended one, because real detection drops the odd onset, so the panel shows both; and `?seed=N` seeds the performance only — the run's key and scenario picks still come from `Math.random`, so two loads of the same link play the same fumbles against a different scenario in a different key.

#### DECISION-016: The drums mark the pulse, and signal the grid one attempt ahead
* **Date:** 2026-08-21
* **Status:** Accepted (extends the provisional percussion of `src/audio/drum-pattern.ts`)
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** The backbeat was a fixed one-measure pattern with eighth-note hats always on. Two problems: the constant eighths blurred the quarter-note pulse the player actually needs to find beat 1, and nothing anywhere told the player that the *next* four measures were sixteenths. By the time the first sixteenth arrives it is far too late to start counting it.
* **Decision:** Split the kit's two jobs. The pulse is quarter notes only — kick on 1 and 3, snare on 2 and 4, **and a hat on every beat with them** — unchanging. Over it, one layer per subdivision present in the current **or next** attempt: hats on the ands for eighths, a bright tick on the `e` and `a` for sixteenths, a pitched woodblock click for triplets. `game/subdivisions.ts` reads the grid off note *positions* rather than duration names, so it stays true for any phrase and works for triplets, which have no `NoteDuration` of their own.
* **The on-beat hat is load-bearing, not decoration.** The first cut of this dropped every hat, on the reasoning that a hat is an eighth-note sound. Playtesting reported "don't hear drums" — and measuring the real output showed why: the beat was firing correctly (one transient per beat, exactly on time), but the peak above 800 Hz, roughly where a laptop or phone speaker begins reproducing, was 0.14 against 0.41 full-band. Two thirds of the kit's energy was sub-bass the player never hears. Restoring an accented hat on each beat and lifting the bus took the audible-band peak to 0.49 with the full-band peak still under 0.75. The suite now taps the master output and asserts all three — no clipping, an audible-band floor, and one transient per beat — because "loud by the numbers, inaudible in the room" is not a failure any unit test can see.
* **Alternatives Considered:** (a) Signalling only the upcoming attempt. Rejected: the marking would stop at the moment it is most needed. Taking the union of current and next means a grid announced early keeps being marked through the phrase that needs it. (b) One voice at different velocities for all three grids. Rejected: sixteenths and triplets can be signalled in the same bar, and telling them apart is the entire point — they are separated by timbre, not volume.
* **Consequences:** Positive — the pulse is unambiguous again, and a hard rhythm announces itself a full attempt before it arrives. The triplet channel is implemented and unit-tested but dormant: no shipped scenario authors a triplet, pinned by a test so the first one that does shows up as a deliberate change. Negative — `setPattern` re-schedules the queued tail on every grid change, so the kit restates itself at some attempt transitions; guarded on a set key so it only happens when the grid actually changes.

Judged not worth blocking the other four parts of the request on, since sequencing is the standard next step after straight runs in any scale-practice regimen and the phrase tables are a two-line change in `scripts/author-rocky-scenarios.mjs` if the call is wrong.
* **Consequences:** Positive — four scenarios stay musically distinct, L1–6 stays covered, and the difficulty ladder means something again; pinned by a registry test that fails if a `_high` level ever becomes a copy of its normal counterpart. Negative — "High" now names the route's position on the mountain rather than the register, which is a small lie in the scenario's *name* that the premise and production notes have to carry.

#### DECISION-012: Collapse the timeline to one octave, root to root
* **Date:** 2026-08-21
* **Status:** Accepted (supersedes the two-octave pitch space in `GOATerizer_Game_Design.md` §13.1)
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** The design specified fifteen lanes over two octaves. In play that is too much to hold in your head and answer on a guitar in real time: fifteen lanes are thin enough that the labels had to be set at 11px, and the exercise spans more neck than one hand position covers.
* **Decision:** The pitch space is eight lanes, one octave root to root. The authored token vocabulary is `1..7` plus `b1` (the octave root); `b2..b7` and `c1` are now `DegreeTokenError`s rather than silently folded notes, so a scenario file written against the old vocabulary fails its validation test instead of transposing an exercise at runtime. Every Rocky-family scenario was re-authored inside the octave, preserving each level's rhythm, note count, route and star thresholds.
* **Alternatives Considered:** Keeping fifteen lanes and only enlarging the labels. Rejected: the user's objection is about what a player can respond to in real time, not about type size, and the tablature stretch (DECISION-014) has the same root cause.
* **Consequences:** Positive — rows are nearly twice as tall, so labels scale with them and nothing has to be hidden for being small; one octave is one hand position. `LOWEST_TONIC_MIDI` moves from E2 (40) to A2 (45), documented as provisional tuning: a one-octave span anchored at the open low E pins every key to first position, where only low-E-rooted shapes are reachable, and A2 puts every key where shapes on three strings fit. Negative — the game's register shifts up for every key, so existing high scores were set against a slightly different exercise; and the two-octave scale, which is a real thing guitarists practise, is no longer expressible until a future design adds a second-octave mode.

#### DECISION-011: Mock the browser's microphone API, not Tuninator's, for synthetic guitar input
* **Date:** 2026-08-20
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** The environment this game is developed and calibrated in cannot grant microphone access, so `TuninatorGuitarInputProvider` — the real detection path calibration depends on — never receives a sample there. The existing `?input=test` deterministic provider bypasses Tuninator entirely and cannot exercise onset detection, confidence gating, or the latency chain.
* **Decision:** Add `?dev=1&input=synth`, which monkey-patches `navigator.mediaDevices.getUserMedia` (a standard browser API) to return a `MediaStream` backed by a synthesized sine oscillator with a guitar-ish attack envelope. `TuninatorGuitarInputProvider` and Tuninator itself are untouched and unaware of the substitution.
* **Alternatives Considered:** Extending `RecognizerOptions` with a caller-supplied `MediaStream`/`stream` field. Rejected: Tuninator's actual `RecognizerOptions.input` type has no such field, and `AGENTS.md` §4 explicitly forbids inventing a Tuninator API GOATerizer does not verify exists.
* **Consequences:** Positive — exercises the real recognizer end-to-end (verified: 261.6 Hz detected, confidence 1.00, 12/0/0 Perfect judged) without touching or assuming anything about Tuninator's surface. Negative — global monkey-patching is inherently fragile if Tuninator ever calls `getUserMedia` through a captured/bound reference instead of a live property lookup; mitigated by dev-only gating and an `uninstall()` path that restores the real API on any switch away from `synth`.

#### DECISION-010: Robust statistics (median/MAD), not a running mean, for the latency-calibration instrument
* **Date:** 2026-08-20
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** `EXTRA_INPUT_LATENCY_MS` calibration requires aggregating per-note timing deltas from a human playing live, but a player calibrating will fumble a note or two.
* **Decision:** `TimingDeltaLog` reports the median and median-absolute-deviation of a rolling 64-sample window, not a mean. Samples are cleared whenever the latency trim changes, and autoplay-sourced samples (discrete or synthetic) are excluded entirely, since both would trivially confirm whatever trim is already set.
* **Alternatives Considered:** A simple running mean. Rejected: one badly-mistimed note drags a mean far enough to make the suggested trim actively wrong, with no signal that this happened.
* **Consequences:** Positive — a single outlier does not corrupt the suggested correction, and `spread` (MAD) gives an honest signal for "not enough samples yet" versus "found a real bias." Negative — median is a coarser statistic than a confidence-weighted estimate would be; acceptable given the sample sizes calibration sessions actually produce.

#### DECISION-005: Fix bass audibility by changing timbre, not register; add synthesized percussion
* **Date:** 2026-08-20
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** The backing bass was inaudible in practice (measured: signal present at peak 0.21, but all energy concentrated at 47-53 Hz, a band most small speakers do not reproduce). The bass is deliberately voiced at 40-75 Hz to sit under the guitar target register — a stated design constraint, not a bug.
* **Decision:** Change the bass oscillator from triangle to sawtooth and raise the lowpass cutoff from 420 Hz to 1200 Hz, preserving harmonics a small speaker can reproduce while leaving the fundamental register untouched. Separately, add a synthesized drum backbeat (kick/snare/hi-hat) as new, explicitly provisional tuning data (`AGENTS.md` §17), since the design specifies no percussion at all and the bass alone did not read as a rhythmic pulse in the audible band.
* **Alternatives Considered:** Voicing the bass higher, into an audible register directly. Rejected: the low register is a stated design decision (documented twice in `bass-line.ts`), and moving it would be the easy fix and the wrong one.
* **Consequences:** Positive — measured through a simulated small-speaker filter: transient rate matches the expected eighth-note pulse (3.86/sec against 4/sec predicted at 120 BPM), where before nothing survived the filter. Negative — percussion is new, unspecified-by-design content; explicitly labeled provisional so it reads as tuning data rather than canonical design if the actual GDD is later extended to cover it.

#### DECISION-003: Windows process spawning — shell for npm, bypass npx entirely for vite
* **Date:** 2026-08-19
* **Status:** Accepted
* **Owner:** Trevor (agent-assisted, Claude Opus 5)
* **Context:** `scripts/setup-tuninator.mjs` and `scripts/browser-validate.mjs` failed on Windows. Naming `npm`/`npx` directly fails with `ENOENT` (`CreateProcess` ignores `PATHEXT`); naming `npm.cmd`/`npx.cmd` then fails with `EINVAL` (Node ≥20.12 refuses to spawn `.cmd`/`.bat` without `shell: true`, per the CVE-2024-27980 hardening).
* **Decision:** For `setup-tuninator.mjs`, which must invoke whatever npm is on `PATH`, enable `shell: true` on win32 only, passing the full command as a single string (every argument is a bare word; the only path involved travels via `cwd`). For `browser-validate.mjs`, which only needs the project's own already-installed Vite, bypass `npx`/shell entirely and invoke `node_modules/vite/bin/vite.js` directly via `process.execPath`.
* **Alternatives Considered:** Using `shell: true` for both scripts uniformly. Rejected for `browser-validate.mjs`: unnecessary risk (submitting a path to `cmd.exe`'s quoting rules) when the target script is already known and on disk.
* **Consequences:** Positive — both scripts now run on Windows; verified `npm run validate:browser` reaches 35/35 driving installed Chrome. Negative — `shell: true` is a real attack surface if arguments ever stop being bare words; scoped narrowly (`WIN32 && command === NPM` only) to keep that risk contained and visible at the call site.

#### DECISION-002: Detect a wrong Tuninator checkout by its exported symbol, not its git ref

* **Status:** Accepted
